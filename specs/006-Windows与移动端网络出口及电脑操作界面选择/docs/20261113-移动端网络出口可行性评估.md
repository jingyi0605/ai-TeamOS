# 移动端网络出口可行性评估

日期：2026-11-13

## 结论

Android 和 iOS 在协议层都可以复用当前的 Desktop Provider 设计：通过 machine credential 建立 device channel，使用 `outcomego-browser-network.v1` 传输 lease、route 和 multiplexed TCP stream，再由移动端打开公共 TCP 连接。

当前不建议直接把 Android 或 iOS 加入正式 `sourceOrder`，原因是移动端缺少 Desktop Provider 已有的稳定后台进程和生命周期保证。建议把移动端拆成后续 Spec，先定义“前台提供”还是“后台持续提供”的产品承诺。

结论分级：

| 平台 | 协议复用 | 前台提供 | 后台持续提供 | 当前建议 |
| --- | --- | --- | --- | --- |
| Android | 高 | 可行 | 条件可行，需要 Foreground Service 和电量/省电验证 | 后续实现 Android 前台 Provider，再评估后台稳定性 |
| iOS | 高 | 可行 | 风险高，需要 Network Extension 或明确的系统授权 | 先做前台实验；后台 Provider 单独立项 |

## 当前代码证据

当前 Desktop Provider 的核心逻辑位于：

- `apps/desktop/src/main/browser-network.ts`
- `apps/desktop/src/main/host/machine-enrollment.ts`
- `packages/plugin-sdk/src/browser-network/client.ts`
- `packages/plugin-sdk/src/browser-network/policy.ts`
- `packages/plugin-sdk/src/browser-network/mux.ts`

它依赖的主要能力是：

1. HTTPS/ WebSocket 出站连接。
2. 本地保存 deployment-scoped consent。
3. machine credential 和 connection ID。
4. 定时 lease renewal。
5. DNS 解析和公共 TCP socket 建立。
6. 网络变化、挂起和恢复后的重连。
7. 将本地 socket 接入 multiplexed stream。

这些能力不要求移动端运行 Linux TUN 或系统级代理。移动端只需要作为 `device` peer 接受服务端转发的公共 TCP 请求。

## Android

### 可复用部分

- `BrowserNetworkClient` 的 lease、epoch、stream window 和 reconnect 协议可以复用。
- Android 可以用 OkHttp 或系统 WebSocket 实现相同的 WebSocket channel。
- Android 可以用系统 DNS 和 `Socket`/`URLConnection`/OkHttp socket 建立公共 TCP 连接。
- 现有 Android 工程已有 Kotlin 客户端、Keystore、WorkManager、FCM 和生命周期适配基础，但尚未有 machine enrollment 或 network provider 模块。

### 必须新增的能力

- Android machine enrollment、machine credential 安全存储和 deployment-scoped consent。
- 长连接 provider 的进程所有权。
- 用户主动打开的 Foreground Service，以及常驻通知。
- 网络变化监听和 WebSocket/stream 重连。
- Doze、省电策略、移动数据切换、Wi-Fi 切换和 VPN 并存测试。
- 公共 TCP 和 DNS 目标的本地 dialer，沿用 `publicOnly` 规则。
- 关闭共享、退出账号、撤销设备和服务端 lease 过期的清理路径。

### 可行产品形态

第一阶段可以支持“用户明确打开网络共享并保持 Foreground Service 运行”。此形态不要求 Android 获得系统级 VPN 权限，因为当前协议只需要移动端按流打开公共 TCP 连接。

如果产品要求即使应用界面关闭、进程被系统回收仍持续提供出口，则需要进一步验证 Foreground Service 类型、通知、厂商省电策略和后台网络限制。不能只依赖普通 Activity 或 WorkManager。

## iOS

### 可复用部分

- 当前 device WebSocket 和 multiplexed stream 协议可以在 Swift 中实现。
- `URLSessionWebSocketTask` 或 Network.framework 可以承担控制连接和公共 TCP 出站。
- iOS 可以使用 deployment-scoped consent 和 Keychain 保存 machine credential。

### 主要限制

- 普通 iOS App 进入后台后可能被挂起，无法保证 lease renewal 和持续 WebSocket。
- 普通 App 的后台执行时间不足以承诺长期 network provider。
- 移动网络、Wi-Fi、系统 VPN、低电量模式和应用挂起会频繁改变连接状态。
- 如果要支持长期后台提供，需要评估 Network Extension、Packet Tunnel Provider、相关 entitlement、用户授权、系统审核和发布限制。

### 可行产品形态

第一阶段可以做“前台共享”：用户保持 OutcomeGo iOS 页面处于前台，应用在页面生命周期内提供公共 TCP 出口。该形态可用于实验和有限场景，但不能宣传为稳定的长期出口。

如果目标是像 Desktop 一样在用户离开应用后仍持续提供出口，需要单独评估 Network Extension 方案和 App Store 发布约束。该方案的权限、后台稳定性和维护成本都明显高于当前 Desktop Provider。

## 安全和协议边界

移动端 Provider 继续遵循现有边界：

- 只接受服务端通过 authenticated device channel 转发的请求。
- 只允许公共、单播、策略允许的 TCP 目标。
- 不提供移动端局域网或私有地址访问。
- 不提供任意 UDP 或 ICMP。
- 连接和 route epoch 变化时销毁旧 stream。
- 用户撤销共享或设备失联后停止接受新连接。

## 后续建议

- `spec007`：Android 前台网络出口 Provider，先完成真实设备上的 enrollment、consent、lease、public TCP 和断线恢复。
- `spec008`：iOS 前台网络出口实验，验证 `URLSessionWebSocketTask`、Network.framework、前台连接和系统网络切换。
- 后续 Spec 必须在确认后台承诺后再决定是否引入 Android Foreground Service 或 iOS Network Extension。
